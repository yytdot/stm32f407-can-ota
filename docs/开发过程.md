# 开发过程记录

这篇不是教程，就是把我从「不知道从哪下手」到「能跑通一次升级」的过程按阶段记下来，包括当时卡住的地方和最后怎么解决的。给以后的自己看，也给正在做类似东西的人一个参考。

---

## 阶段一：先想清楚要不要 Bootloader

一开始我只想「写个程序能收 CAN 就行」，后来发现不行：升级的时候必须要有一个**不参与升级**的程序在那儿看着，不然把正在运行的程序擦了，谁来接收新固件？

所以结构定成两个工程：

- Bootloader：上电先跑，判断要不要升级，不升级就把控制权交给 App
- App：真正干活的程序，有 FreeRTOS，有传感器、OLED、CAN 广播

这两个是**独立的 Keil 工程**，各自编译、各自烧录，不是一个大工程里用宏切换。这样 Bootloader 的体积好控制，也不会把 FreeRTOS 那一堆东西带进去。

## 阶段二：给 Flash 分区

F407ZGT6 是 1MB Flash。查手册才知道它按 Sector 擦，Sector 0~3 是 16KB、Sector 4 是 64KB、Sector 5~11 是 128KB，擦除最小单位就是一整个 Sector，不能按字节擦。

于是 Bootloader 放 Sector 0~4（正好 128KB），App 从 Sector 5 开始（0x08020000），7 个 128KB 共 896KB。

这部分我单独抽了个 `Common/flash_layout.h`，所有地址都写在这里。原因是之前踩过坑：Bootloader 里写一个 0x08020000，App 的 IROM1 里又写一个，向量表偏移再写一个，改的时候漏一处就跳飞。

## 阶段三：Bootloader 工程从零搭

App 那边是 CubeMX 生成的，外设初始化都有人管。Bootloader 我一开始也想用 CubeMX 生成，后来发现两个问题：

1. 生成的代码带一堆用不到的外设（UART4、DMA、IWDG……），Bootloader 只要 CAN、SPI、两个 LED、一个按键，带进来纯属浪费空间；
2. 生成出来的 `main.c` 会把 `main()` 也占了，跟我的逻辑打架。

最后决定 Bootloader 全部手写。这就带来一个很实际的问题：**没有 `stm32f4xx_hal_msp.c`，SPI1 的 PA5/PA6/PA7 复用、CAN 的 PA11/PA12 复用，全得自己配。**

我是把 `w25q64_init()` 写成「先配 GPIO，再配 SPI 参数」的形式：

- PA4 做 CS，普通推挽输出（软件控制，不能用硬件 NSS，否则时序不好控）
- PA5/PA6/PA7 复用成 AF5（SPI1）
- 然后才填 `SPI_HandleTypeDef`，调 `HAL_SPI_Init()`

当时还疑惑过：HAL 库不是都封装好了吗，为什么 CS 还要我自己拉？后来想明白了：**HAL 管的是 STM32 内部的 SPI 控制器**（时钟、极性、收发、错误），而 CS 是外部芯片的片选，W25Q64 什么时候开始收命令、什么时候结束，是芯片手册规定的时序，HAL 不知道你接的是什么芯片，自然管不了。

## 阶段四：调 W25Q64 驱动

第一步是读 JEDEC ID（命令 0x9F，应该回 0xEF 0x40 0x17）。第一次一直读到 0xFF，排查了半天：

- 先量线：CS、SCK、MOSI 都有波形，MISO 一直是高
- 再看 CS：忘了在发命令前拉低，芯片根本没被选中
- 又发现 SPI 初始化时把 NSS 设成了硬件模式，PA4 被 SPI 外设接管，我代码里拉 GPIO 没效果

改完这三处才读出 ID。从那以后我的驱动里都是：`CS_LOW()` → 发命令 → 读/写 → `CS_HIGH()`，一个函数一个完整事务，中间不做别的。

写操作用的是「页编程 + 轮询忙标志」：

- W25Q64 一页 256 字节，跨页写会回卷，所以写之前要按页切开
- 每次写完要读状态寄存器 bit0（BUSY），等它变 0 才能发下一条命令
- 这个等待是 do-while 轮询，因为擦除一个 4KB 扇区要几十毫秒，不查忙标志直接发下一条命令必然失败

## 阶段五：定 OTA 协议

CAN 一帧最多 8 字节，还要区分「这是命令还是数据」，所以第一字节当了命令字。

方向用两个扩展帧 ID 分开：`0x18F00001` 是上位机发给设备的，`0x18F00002` 是设备回给上位机的。过滤器就只放行前者，别的一律不进队列。

命令字一共 6 个：握手、固件头、数据、重传、校验、重启，应答就是命令字 | 0x80，出错统一回 0xFE。

数据帧的格式：`[命令字][序号][5 字节数据][CRC8]`，正好 8 字节。

- 序号用来发现丢帧，上位机发现序号跳了就让设备重传
- CRC8 多项式 0x07，算前面 7 个字节，防的是总线干扰
- 每帧设备都要回 ACK，上位机收不到就超时重传，最多 3 次

握手这里有个小细节：判断条件必须是 `DLC == 1 且 data[0] == 0x01`。一开始只判断了 `data[0]`，结果数据帧的第一个字节刚好是 0x01 的时候，设备误以为要升级，直接复位了。加上 DLC 判断才稳。

## 阶段六：片内 Flash 擦写

这块是整个项目里最难的，也是花时间最多的。

**第一个问题：擦的时候程序跑飞。**

代码本身在 Flash 里，`HAL_FLASHEx_Erase()` 执行的时候 CPU 还要从 Flash 取指令，而擦除期间 Flash 是读不了的。第一次测试直接 HardFault。

解决：把 `flash_erase_app()`、`flash_write()`、`flash_program_firmware()` 都加上

```c
__attribute__((section(".ram_code")))
```

让它们链接到 SRAM 里执行，启动时由启动文件把这段从 Flash 拷到 0x20000000 区。这样擦 Flash 的时候，执行代码在 RAM 里，不受影响。

**第二个问题：写数据必须是 4 字节对齐，还要凑够一个 word。**

`HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, ...)` 一次写 32 位，地址不对齐直接报错。所以 `flash_write()` 里面是一个字节一个字节往 `uint32_t` 里拼，拼满 4 个再写。

这里当时纠结过一个点：**为什么不先把 `word_data` 清零再拼？**

因为它初值必须是 `0xFFFFFFFF`。Flash 擦完之后每个字节都是 0xFF，写的时候只能把 1 变成 0。如果初值给 0，最后一块数据不满 4 字节的时候，剩下那几个字节就会被写成 0x00 —— 等于把不该动的位置强行清零了，而且 Flash 擦之前改不回来。用 0xFF 当初值，没填到的位置就是「不改变」，才是对的。

**第三个问题：一次搬多少。**

最早想一次把整个固件从 W25Q64 读到 RAM 再写，不行，RAM 不够。后来改成 4KB 一块：

```c
static uint8_t chunk_buf[4096];   // 放 .bss，不能和 .ram_code 抢地方

while (total < fw_size) {
    len = min(4096, fw_size - total);
    w25q64_read(offset + total, chunk_buf, len);
    flash_write(APP_START_ADDR + total, chunk_buf, len);
    total += len;
}
```

4KB 正好是一个 W25Q64 扇区，读的时候不会跨扇区，也不会把栈撑爆。

## 阶段七：跳转 App

跳转有三个必须做的事，少一个就死：

1. 关掉所有中断（`__disable_irq()`），不然跳过去以后中断向量还是 Bootloader 的
2. 把 MSP 设成 App 向量表的第一个字：`__set_MSP(*(uint32_t*)APP_START_ADDR)`
3. `SCB->VTOR = APP_START_ADDR`，让 App 自己的中断能找对入口

App 那边也要配合：CubeMX 里 IROM1 起始地址设成 0x08020000，`VECT_TAB_OFFSET` 设成 0x20000，启动文件里的向量表偏移跟着改。

第一次跳转失败是 HardFault，原因就是 App 的 IROM1 还是 0x08000000，编译出来的程序按 0x08000000 链接，Bootloader 跳到 0x08020000 当然找不到正确的中断入口。改完重新编译就好了。

## 阶段八：App 侧的任务划分

App 用的是 FreeRTOS，一开始所有东西都塞在一个 while(1) 里，结果 OLED 刷新的时候传感器就不读了，CAN 也卡。后来拆成 4 个任务：

| 任务 | 优先级 | 周期 | 干什么 |
|---|---|---|---|
| task_can | 3（最高） | 1000ms 广播 | 收 CAN 帧、判断是不是升级命令、周期广播传感器数据 |
| task_sensor | 1 | 500ms | 读 SHT30、BH1750、ADC |
| task_oled | 1 | 等队列 | 收到数据才刷屏 |
| task_key_led | 0（最低） | 100ms | 按键长按检测、运行灯翻转 |

传感器读到的数据要同时给 OLED 和 CAN 用，所以开了**两个队列**，`task_sensor_create()` 调两次，每次传一个队列进去。这样一个生产者、两个消费者，谁慢都不影响采集。

OLED 那边用的是阻塞等（`portMAX_DELAY`），没数据就睡，不占 CPU。

## 阶段九：联调

联调阶段的现象和排查：

- **发握手，设备不回 ACK**：先确认滤波器放行的 ID 对不对（32 位列表模式，`FilterIdHigh/Low` 拼装容易错），再看是不是两块板没共地
- **偶尔丢帧、CRC 报错**：CAN 两端没接 120Ω 终端电阻，示波器上看波形有反射
- **升级到一半卡住**：上位机等 ACK 的超时时间比设备写 W25Q64 的时间还短（写一页要几毫秒），把超时从 200ms 调到 1000ms 才稳定
- **升级完成但跑的还是旧程序**：`CMD_REBOOT` 之前没重算 CRC32，校验那一步其实没通过，状态机停在 VERIFY 了

最后跑通的顺序是：长按按键 → OLED 灭、灯变慢闪 → 上位机发握手收到 0x81 → 发头收到 0x82 → 发数据一路 0x83 → 发校验收到 0x85 → 灯常亮两三秒 → 灯全亮 → 新程序跑起来，OLED 重新亮。

那一刻还是挺爽的。

## 阶段十：回头看

现在再看，有几个地方当时做得不够好：

- 数据帧只带 5 字节，效率低，改成 6~7 字节能快不少
- 没有断点续传，断了只能从头传
- 升级过程没有进度显示，只能靠数 ACK
- 错误码分得太粗，所有失败都是 0xFE，不好定位
- PC 上位机还没正经写，现在是用手拼帧在测

这些准备后面继续补。
